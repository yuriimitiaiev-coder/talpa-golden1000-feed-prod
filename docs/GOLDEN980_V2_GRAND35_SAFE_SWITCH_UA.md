# TALPA Golden980 V2 — рішення про відмову від Гранд Інструмент, 01.11.2026

## Затверджено власником
Повністю замінити **35 ACTIVE SKU Grand Instrument** в Prom.ua на **23 SIGMA + 12 ZaInstrumentom**, не змінюючи кількість Golden980.
Принцип: **945 старих SKU зберігаються, 35 вилучаються, 35 створюються**; статус = **980 ACTIVE + 20 вільних місць**.

## Підготовлені перевірені артефакти (draft PR #24)
- `data/grand35_to_remove_FROM_PROM_READ_ONLY.csv` — точні 35 старих артикулів і Prom UID. Це **не файл для імпорту**.
- `data/grand35_replacement_selected.csv` — 35 нових артикулів, актуальні фіди, РРЦ і доступність, товарні групи, 23/12. Закупівельні ціни для цих 35 не підтверджені в цьому файлі; відбір не є доказом маржинального доходу.
- `data/golden980_production_candidate.csv` — тестовий новий пул 980 SKU: 655 SIGMA + 325 ZaInstrumentom, 0 Grand.
- `data/approved_golden980_v2_PENDING_PROM_UID.csv` — 945 незмінних Prom UID та 35 позицій з порожніми Prom UID, які можна заповнити тільки після фактичного створення нових карток у Prom.
- `scripts/build_grand35_prom_import.py` створює окремий **35-товарний YML XML** для одноразового завантаження в Prom із назвами, фотографіями, цінами і категоріями. Для SIGMA в цьому тимчасовому файлі використовуються оригінальні фото постачальника: нові дзеркальні адреси TALPA Pages ще не опубліковано.
- GitHub Actions PR run **41316915954**: 980 new-pool build PASS, 35-only XML import PASS, audit/tests PASS. Артефакт `Golden980-v2-add35-ONLY`, скачати через секцію Artifacts цього запуску. **Не плутати зі стандартним 980-товарним XML production URL**.

## Блокування на production
- Draft PR #24 **НЕ ЗЛИВАТИ**, поки немає внутрішніх ID Prom для кожного нового товару.
- `scripts/validate_golden980_output.py` навмисно зупиняє production збірку, коли для нових SKU немає Prom UID (умова `PRODUCTION HOLD`). У PR тестове середовище може працювати з рівно 35 очікуваними новими SKU.
- Поточний production GitHub main і посилання на XML поки мають старі 632/313/35 і не змінюються.

## Безпечний порядок одного переходу, жодних проміжних >1000 карток
1. Переконатися, що 35 нових мають придатну маржу за персональними закупівельними цінами TALPA, враховуючи податки й витрати, якщо мета — прибутковість. Оцінка лише за РРЦ недостатня.
2. Підготувати й скачати окремий **35-only** XML із тестової збірки та мати перед очима реєстр 35 старих карток.
3. Безпосередньо перед ротацією **вимкнути автоматичне оновлення чинного GitHub-URL у Prom** (`Ніколи`) і **ЗБЕРЕГТИ налаштування**. Переконатися після відкриття, що `Ніколи` збереглося. Інакше старий 4-годинний фід поверне Grand-картки, які ми видалимо.
4. Масово вилучити **тільки ці 35** старих Prom SKU (точні UID з CSV). Контролювати кількість **945**.
5. **Одноразовий імпорт з комп'ютера** тільки нового `grand35_add_35_only_PROM_IMPORT.xml`. Завантаження *нових* товарів потребує назв, фото, ціни, наявності, кількості й груп. Встановити `Статус товарів, яких немає у файлі: Залишити без змін`. НЕ ставити `Тільки оновлення` (це заблокувало би створення). Не використовувати 980-товарний production фід для первинного створення 35 карток.
6. Завантажити новий експорт Prom й порівняти всі 980 SKU/UID/зовнішні ID та всі інші поля; перевірити рівно 35 нових UID, відсутність всіх Grand, 945 збережених карток і рівно 980 карток, фото і групи нових.
7. З експортом заповнити 35 внутрішніх UID у master V2, ще раз тестувати production gate, потім **merge** і чекати GitHub Pages deploy PASS. Підтвердити public XML точно 980 = 655+325.
8. Після публікації відновити в Prom регулярний імпорт того самого GitHub URL **раз на 4 години**, лише `ціна, наявність, кількість`, `Залишити без змін` для відсутніх; інші поля без оновлення; перевірити збереження налаштувань і наступний автоматичний звіт.
9. Підсумковий експорт 980 і перевірка цін/наявності. Ні в одному кроці не змінювати автоматично товарний склад понад затверджені 35 замін.

**Не запускати пункти 3–9 навмання.** Зберегти backup поточного export 980 і old feed. Якщо створення 35 товарів не вдається, залишити автозавантаження вимкненим до усунення проблеми й відновити старі картки з backup, не намагатися повернути їх неконтрольованим 980-XML імпортом.
